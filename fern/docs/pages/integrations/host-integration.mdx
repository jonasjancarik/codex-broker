# Host integration

Product backends and job workers can use the native owner-scoped API or the
OpenAI-compatible API. Browser clients normally keep calling the host app.

Your backend remains the public product API. The broker is private infrastructure behind it.

## Choose the API surface that matches the host

| Surface | Best fit | Identity |
| --- | --- | --- |
| Native owner-scoped API | Product backends that need explicit threads, turns, event replay, interactions, auth management, bundles, and audit routes | Internal broker key plus server-selected `ownerId` |
| OpenAI-compatible API | Existing OpenAI SDK integrations that need text or image Responses or Chat Completions without adopting broker-specific request shapes | Compatibility key mapped to a fixed server-side binding |

Both surfaces use the same scheduler, Codex profiles, policy, app-server pool,
and durable state. The compatible surface intentionally exposes fewer controls.
See [OpenAI compatibility](openai-compatibility.mdx) for its exact contract.

## Boundary

The host app is still responsible for:

- product authentication and authorization
- user, chat, job, and artifact records
- UI streaming and rendering
- prompt construction and product memory
- evidence search and domain-specific tools
- final authorization checks inside hosted tool endpoints

The broker handles:

- Codex auth homes per auth principal and profile
- app-server process pooling and JSON-RPC routing
- broker thread and turn lifecycle
- one-active-turn-at-a-time locking
- normalized event persistence and streaming
- bundle materialization for skills, prompts, MCP servers, and broker-hosted adapters

## Stable ids

Choose stable product ids and send them consistently:

| Field | Purpose |
| --- | --- |
| `ownerId` | Product user, tenant, or service account that owns broker state and audits. |
| `authPrincipalId` | Optional assertion of the Codex account selected by trusted host policy. Omission defaults to `ownerId`. |
| `profile` | Codex auth profile under the resolved principal. Defaults to `default`; immutable per broker thread. |
| `threadId` | Broker thread id. You may supply a stable chat or job id on create. |
| `turnId` | Broker turn id returned from turn creation. |
| `productCorrelationId` | Optional host trace id for events and logs. |
| `idempotencyKey` | Host retry key for a retriable turn request. |

Avoid raw secrets as owner ids. Use a service-account id when per-user auth is not needed.

Configure shared accounts with `CODEX_BROKER_AUTH_PRINCIPAL_MAP_JSON` or its file equivalent. A client-supplied principal must match policy or the broker returns `403`. Two mapped owners share credentials and upstream totals, never threads, events, interactions, or audits.

## Native turns can carry inline images

Native turn input is forwarded to Codex as an ordered list. Mix text items with
`type: "image"` items, or send images alone. An inline image uses a base64 data
URL in `url`; a native `localImage` item can instead refer to a path readable by
the Codex runtime. Native turn-create and steer JSON bodies may be up to 32 MiB.

```json
{
  "input": [
    { "type": "text", "text": "Describe this image." },
    {
      "type": "image",
      "url": "data:image/jpeg;base64,<base64-bytes>",
      "detail": "auto"
    }
  ],
  "mode": "queue"
}
```

## Chat apps

Chat integrations usually follow this flow:

1. Resolve the logged-in product user to a stable `ownerId`.
2. Create or reuse a broker thread for the host chat.
3. Submit chat messages with `mode=queue` when same-chat turns should serialize, or `mode=steer` when the UI intentionally appends input to an active turn.
4. Stream `/events` from the host backend and map normalized events to the product stream protocol.
5. Keep evidence search and product tools as host-owned HTTP endpoints or MCP servers declared by a bundle.

The host keeps chat records, product prompts, evidence behavior, and UI streaming. The broker handles auth, pooling, thread locks, and bundle mounting.

## Job workers

Worker integrations usually follow this flow:

1. Use the job's product user id or a service account as `ownerId`.
2. Store the broker `threadId` alongside the job.
3. Submit initial and follow-up work with `mode=queue`.
4. Poll the turn or stream events into job logs and artifacts.
5. Use `codexOptions.outputSchema` when the final assistant message must match a JSON Schema.

The worker keeps queue records, generated files, artifact storage, and review rows. The broker runs the Codex side of the job.

## Model, reasoning, and Fast per turn

First discover the selected account's available choices:

```http
GET /v1/owners/{ownerId}/auth/models?profile=default
```

The response preserves App Server's supported/default reasoning efforts and service tiers, modalities, personality support, picker visibility, default state, and upgrade metadata. It returns `nextCursor` for pagination. Pass the selected entry's `model` slug as `codexOptions.model`; `id` is the stable catalog preset identifier. Offer Fast only when the selected model advertises a `serviceTiers` entry with `id: "fast"`.

Set the selected choices in the turn body:

```json
{
  "input": [{ "type": "text", "text": "Review these changes." }],
  "codexOptions": {
    "model": "gpt-5.6-sol",
    "effort": "high",
    "serviceTier": "fast"
  }
}
```

Selection precedence is the turn's `codexOptions`, then the selected `configProfile`, then Codex's current recommended model and model-specific defaults. A turn-level choice does not modify the profile. `reasoningEffort` is accepted as an alias for `effort`. Use `/auth/models` instead of hardcoding supported efforts or service tiers.

## Native API authentication stays server-side

Native product routes require one of these headers:

```http
Authorization: Bearer <CODEX_BROKER_INTERNAL_KEY>
X-Codex-Broker-Key: <CODEX_BROKER_INTERNAL_KEY>
```

Only `GET /healthz` and `GET /readyz` are unauthenticated. `/metrics`,
`/openapi.json`, `/v1/owners/...`, and `/v1/bundles/inline` require the broker
key unless the broker is running with
`CODEX_BROKER_ALLOW_UNAUTHENTICATED=true`.

Keep the broker key server-side. Browser `EventSource` cannot set the required auth header, so product UIs should consume a host-owned proxy stream.

OpenAI-compatible routes always require their own compatibility bearer key.
Unauthenticated development mode does not bypass that check, and native and
compatibility keys are not interchangeable.

## Auth states

`GET /auth/status` runs Codex's local login-status check. `POST /auth/probe` runs a tiny real Codex request and persists `refresh_failed` when token refresh is invalidated.

`GET /auth/profiles` lists persisted last-recorded profile state without invoking Codex. The thread's principal, canonical profile, and profile instance cannot change. To replace an account, quiesce every sharing owner, logout with `deleteProfile: true`, authenticate the replacement, and create a new broker thread id; old and queued threads fail closed.

Auth status can be:

- `missing`
- `present_unverified`
- `authenticated`
- `invalid`
- `refresh_failed`
- `failed`
- `unknown`

Failed turns include `errorCode`, `publicMessage`, and `adminMessage`. Host UIs should show `publicMessage` or `error` to end users and keep `adminMessage` for admin-only logs.

## Production checklist

- Call the broker only from trusted server-side code.
- Keep owner-to-principal mapping in trusted deployment configuration.
- Select `profile` on thread creation and never use a turn to switch it.
- Store broker `threadId` next to product chat or job records.
- Send caller-owned `threadId` values when idempotent host mapping matters.
- Send `productCorrelationId` and `idempotencyKey` on retriable product actions.
- Stream with `after=<last-event-id>` when reconnecting.
- Handle terminal events and terminal turn statuses.
- Validate hosted-tool secret headers in the host app.
- Keep product authorization inside the host app, including hosted tool endpoints.
- Prefer configuration profiles and reviewed bundles over ad hoc per-request behavior.
- Give each OpenAI-compatible client the narrowest practical server-side binding.
