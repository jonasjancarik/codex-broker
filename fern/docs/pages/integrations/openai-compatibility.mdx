# The supported OpenAI API subset works as a drop-in endpoint

Codex Broker exposes a defined subset of the OpenAI API. Existing
OpenAI SDK clients can use the supported text, image, and function-tool
workflow by changing their base URL and API key; the broker then runs the
request through its existing Codex identity, scheduler, persistence, and
app-server controls.

This is not a claim of compatibility with every OpenAI endpoint or parameter.
The broker accepts behavior it can reproduce faithfully and returns an
OpenAI-shaped error for everything else.

## Change only the base URL and compatibility key

Python:

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:3400/v1",
    api_key="a-compatibility-key-issued-by-the-operator",
)

response = client.responses.create(
    model="gpt-5.6",
    input="Explain this change in two sentences.",
)
print(response.output_text)
```

TypeScript:

```typescript
import OpenAI from "openai";

const client = new OpenAI({
  baseURL: "http://127.0.0.1:3400/v1",
  apiKey: process.env.CODEX_BROKER_COMPATIBILITY_KEY,
});

const response = await client.responses.create({
  model: "gpt-5.6",
  input: "Explain this change in two sentences.",
});
console.log(response.output_text);
```

The compatibility key is not the internal broker key and is not the upstream
credential stored in a Codex auth profile. Each credential is accepted only on
its own boundary.

## Compatibility keys select identity and policy on the server

Set `CODEX_BROKER_OPENAI_COMPAT_BINDINGS_FILE` to a JSON file whose keys are
lowercase SHA-256 digests prefixed with `sha256:`:

```json
{
  "sha256:<digest-of-client-key>": {
    "ownerId": "service-account-1",
    "authPrincipalId": "shared-codex",
    "profile": "default",
    "configProfile": "default",
    "hostApp": "openai-sdk",
    "bundleId": "example-chat-v1",
    "cwd": "/workspaces/app"
  }
}
```

Generate the digest without writing the raw key into the binding file:

```bash
printf '%s' "$COMPATIBILITY_KEY" | shasum -a 256
```

`ownerId` is required. The other fields are optional:

| Field | Default | Effect |
| --- | --- | --- |
| `authPrincipalId` | owner policy default | Selects the trusted Codex credential principal. It must still satisfy the broker's owner-to-principal policy. |
| `profile` | `default` | Selects the Codex auth profile. |
| `configProfile` | `default` | Selects broker execution defaults and policy. |
| `hostApp` | `openai-compatible-api` | Labels the integration in broker records and diagnostics. |
| `bundleId` | none | Enables one reviewed Codex bundle for this caller. |
| `cwd` | none | Fixes the allowed Codex working directory. |
| `modelAliases` | `{"gpt-5.6": "gpt-5.6-sol"}` | Custom entries extend this built-in mapping. An explicit entry with the same name overrides the default for this binding. |

The `gpt-5.6` alias works without a `modelAliases` field. Omitting the field or
setting it to `{}` keeps the built-in default. For example, configuring
`"modelAliases": {"fast": "gpt-5.6-luna"}` adds `fast` while keeping
`gpt-5.6` mapped to Sol. Aliases are advertised and usable only when their
targets are available in Codex's model catalog; canonical model names also work
directly.

The raw key is distributed separately to the client. The broker keeps only its
digest in configuration and never persists the presented key or its digest in
turn records. Request bodies and custom headers cannot override the binding's
owner, principal, profiles, host app, bundle, workspace, or aliases.

See [Configuration reference](../operations/configuration-reference.mdx#openai-compatible-identity-bindings)
for the complete environment contract.

## The Responses API is the primary compatibility surface

| Endpoint | Supported behavior |
| --- | --- |
| `GET /v1/models` | Lists direct model names and aliases available to the binding. |
| `GET /v1/models/{model}` | Retrieves one available direct model or alias. |
| `POST /v1/responses` | Creates synchronous or streamed responses from text, image, and function-call input. |
| `GET /v1/responses/{responseId}` | Reconstructs a persisted compatible response. |
| `GET /v1/responses/{responseId}/input_items` | Lists the normalized text and image input persisted for a response. |
| `POST /v1/responses/{responseId}/cancel` | Interrupts an active response and returns its updated state. |
| `POST /v1/chat/completions` | Provides synchronous or streamed Chat Completions from text, image, and tool messages. |

Completed responses prefer Codex raw response items when available. Codex
versions that omit those events are reconstructed from their persisted
completed agent-message events, so synchronous responses remain retrievable
after a broker restart.

Responses requests accept:

- `model`
- a non-empty string input, or message items with ordered text and user-only image content ending in a user message
- `instructions`
- `stream`
- `previous_response_id`
- `reasoning.effort` and `reasoning.summary`
- `service_tier`
- `text.format` with `text` or `json_schema`
- string-to-string `metadata`
- omitted `store` or `store: true`
- function `tools`, `tool_choice` of `auto` or `none`, `parallel_tool_calls: true`,
  and `function_call` / `function_call_output` input items (see
  [Function tools](#function-tools-run-in-the-client))

JSON Schema output is passed to Codex as an enforceable app-server
`outputSchema`:

```python
response = client.responses.create(
    model="gpt-5.6",
    input="Return the repository status.",
    text={
        "format": {
            "type": "json_schema",
            "name": "repository_status",
            "schema": {
                "type": "object",
                "properties": {
                    "summary": {"type": "string"},
                    "clean": {"type": "boolean"},
                },
                "required": ["summary", "clean"],
                "additionalProperties": False,
            },
            "strict": True,
        }
    },
)
```

Responses image input uses a base64 data URL in a user content item. The broker
accepts `input_text` and `input_image` items in their supplied order, including
image-only user messages. The selected model must advertise image input support.
Only PNG, JPEG, WEBP, and GIF data URLs are accepted; remote URLs, file IDs, and
local file paths are not accepted on the compatible API. The optional `detail`
value may be `auto`, `low`, `high`, or `original`.

The pinned Codex runtime can omit images requested with `detail: "low"`.
Broker therefore sends `high` to Codex for those images, including when replaying
history, while keeping the requested `low` value in stored input and
`input_items` responses. This preserves the image but does not preserve OpenAI's
low-detail processing or token budget. The same mapping applies to Chat
Completions and native turn-create and steer requests.

```python
import base64
from pathlib import Path

image_data = base64.b64encode(Path("receipt.png").read_bytes()).decode("ascii")
response = client.responses.create(
    model="gpt-5.6",
    input=[
        {
            "role": "user",
            "content": [
                {"type": "input_text", "text": "Extract the receipt text."},
                {
                    "type": "input_image",
                    "image_url": f"data:image/png;base64,{image_data}",
                },
            ],
        }
    ],
)
print(response.output_text)
```

For a Karakeep-style OCR workflow, send each image as an `input_image` item
alongside the extraction instruction and persist the returned text in the host
application. Codex Broker does not provide an embeddings endpoint; create or
query embeddings in the host application if that workflow needs semantic search.

## Chat Completions supports ordered text and image content

Chat Completions accepts:

- `messages` whose user `content` is text, images, or an ordered mixture of both,
  including image-only content
- `system` and `developer` instructions
- `stream`
- `reasoning_effort`
- `service_tier`
- string-to-string `metadata`
- `response_format` with `text` or `json_schema`
- `stream_options.include_usage`
- function `tools`, `tool_choice` of `auto` or `none`, `parallel_tool_calls: true`,
  assistant messages with `tool_calls`, and `tool` messages with `tool_call_id`

```python
completion = client.chat.completions.create(
    model="gpt-5.6",
    messages=[
        {"role": "system", "content": "Answer concisely."},
        {
            "role": "user",
            "content": [
                {"type": "text", "text": "What does this screenshot show?"},
                {
                    "type": "image_url",
                    "image_url": {
                        "url": "data:image/jpeg;base64,<base64-bytes>",
                        "detail": "auto",
                    },
                },
            ],
        },
    ],
)

print(completion.choices[0].message.content)
```

Responses should be preferred for new integrations. Chat Completions exists for
applications whose current abstraction is message-based. Its `detail` value may
be `auto`, `low`, `high`, or `original`.

## Function tools run in the client

Clients can declare their own functions with `tools`. The model decides whether
to call them; when it does, the response ends with the calls and your application
runs them, exactly as with OpenAI. The follow-up request carries the whole
conversation plus the results, and the model continues from there.

```python
import json

tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "Look up the current weather for a city.",
            "parameters": {
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"],
            },
        },
    }
]
messages = [{"role": "user", "content": "Is it raining in Prague?"}]

first = client.chat.completions.create(model="gpt-5.6", messages=messages, tools=tools)
choice = first.choices[0]
if choice.finish_reason == "tool_calls":
    messages.append(choice.message)
    for call in choice.message.tool_calls:
        args = json.loads(call.function.arguments)
        messages.append(
            {"role": "tool", "tool_call_id": call.id, "content": lookup_weather(args["city"])}
        )
    final = client.chat.completions.create(model="gpt-5.6", messages=messages, tools=tools)
    print(final.choices[0].message.content)
```

What the broker supports:

| Feature | Behavior |
| --- | --- |
| Tool declarations | `type: "function"` with `name`, optional `description`, and a JSON Schema object as `parameters`. Names must match `^[A-Za-z0-9_-]{1,64}$`; `mcp` and `mcp__*` are reserved by Codex. At most 128 tools per request. |
| `tool_choice` | `auto` (the default) lets the model decide. `none` keeps the tools from the model for that request; earlier tool calls and results in the history still count. |
| Several calls at once | All raw function calls from a response are returned together. Code-mode callbacks dispatched within a short handoff window are also collected. Codex can serialize script calls, so a response may still contain only one. `parallel_tool_calls` may be omitted or `true`. |
| Call ids | Treat `id` / `call_id` as opaque. Code-mode calls use ids such as `exec-4f2c…`. |
| Usage | Usage covers the model response that asked for the tools. If Codex reports none for it, `usage` is `null` on a tool-call response. |
| Text before calls | Text the model writes before calling a tool is returned as the message `content` (Chat) or a message output item (Responses). Otherwise Chat `content` is `null`. |
| Finish reason | Chat Completions report `finish_reason: "tool_calls"`; Responses return `function_call` output items with status `completed`. |
| Streaming | Chat streams the standard `tool_calls` deltas: the first chunk for each call has `index`, `id`, `type`, and the function name, and the next carries the complete `arguments` string. Responses streams `response.output_item.added`, `response.function_call_arguments.delta`, `response.function_call_arguments.done`, and `response.output_item.done`. Calls appear once the model has finished its response, so arguments arrive in one delta rather than token by token. |
| Tool results | Chat `tool` messages take a string or text parts. Responses `function_call_output` items take a string or `input_text` parts. Images in tool results are not accepted; send them in a following user message instead. |
| Responses chaining | A request with `previous_response_id` can answer the previous response's calls with `function_call_output` items. |

Requests that Codex cannot honor fail with `400 unsupported_parameter`:
`tool_choice: "required"` or a named function (Codex cannot force a call),
`parallel_tool_calls: false`, `strict: true` on a function (Codex does not
enforce strict schemas for caller-defined tools; `strict: false` is accepted),
and tool types other than `function`. A history in which a tool call has no
result, or a result answers no earlier call, fails with `400 invalid_parameter`.

### Continue waiting tool calls without regenerating the script

Batching and continuation solve different problems. Batching returns multiple
already-dispatched calls together. Continuation lets an existing script proceed
when your client supplies a result, even when only one call is dispatched at a
time. Neither requires client-specific request fields.

By default, a follow-up still replays history on a fresh Codex thread. Operators
can set `CODEX_BROKER_OPENAI_TOOL_CONTINUATIONS=true` to keep waiting executions
for bindings without a bundle. The client continues sending standard Chat
messages or Responses input. A matching follow-up supplies its tool results to
the same running Codex turn. Each HTTP response has its own ID and stored broker
turn record, on the existing broker thread. Native thread APIs are unchanged.

Matching checks the authenticated binding, account/profile identity, model,
instructions, tools, settings and complete conversation history. Supply every
returned tool result exactly once. Edited histories, changed settings, expired
waiters, lost runtimes and broker restarts fall back to replay; invalid or
partial histories still fail validation. Identical retries share one response;
conflicting results for a follow-up already accepted are rejected. Retry
receipts are process-local, expire after the idle timeout and are capped at 256.
A failure after results may have been delivered is returned without silently
restarting the work.

Waiting executions expire after five idle minutes or thirty minutes of total
chain age by default. Limits are one per owner and two globally, with one App
Server pool slot reserved for other work. A finite pool of one therefore does
not retain waiters. Waiting uses a pool lease, but releases the inference worker.
See the [configuration reference](../operations/configuration-reference.mdx#turn-execution-and-pooling)
for settings. Cancel a completed Responses tool handoff to release its waiting
execution; its stored response remains available. Closing a stream does not
cancel it, so an abandoned waiter expires normally.

Usage counts new model generations for each response. A follow-up that advances
an already-generated script can legitimately report zero tokens. Retention
preserves the script and reasoning in the upstream process; it does not expose
that private state in the client's conversation history.

### Built-in Codex tools are off unless a bundle allows them

A client that brings its own functions expects a model that calls those
functions, not one that runs commands on the broker's machine. When a request
declares `tools` or replays earlier tool calls, and the compatibility binding
has no `bundleId`, the broker starts the Codex thread and turn without an
execution environment, which removes shell commands, file edits, image viewing,
and permission requests. It also turns those tools off in the thread's
configuration, together with web search, sub-agents, questions to the user,
goals, image generation, apps, plugins, and tool suggestions.

What remains is what the model needs to reach your functions: on code-mode
models, the `exec` and `wait` tools that run a short script calling them, and
Codex's read-only resource helpers and, for some models, a clock. Resource
helpers returned empty lists on the tested Pearwrite binding. The V8 runtime
has no Node, filesystem or network APIs; the native host remains trusted and
is not wrapped in the command tool's Bubblewrap sandbox.

A binding with a reviewed bundle keeps that bundle's skills, MCP servers,
hosted tools, and sandbox policy alongside the caller's functions, because the
operator assigned them. Caller-defined functions never grant or select bundle
capabilities.

## Image and token limits are explicit

For images supplied in the current request, the compatible API enforces at most
10 images, no more than 20 MiB per image, and no more than 20 MiB total decoded
image data. The JSON request body limit for compatible Responses and Chat
Completions requests is 32 MiB. These limits count images supplied in the current
request; previously stored images are also replayed when chaining responses with
`previous_response_id`. Native turn-create and steer requests also allow 32 MiB
JSON bodies. Other routes retain the default 1,000,000-byte limit.

Chat Completions accepts `max_tokens` and `max_completion_tokens` for client
compatibility, then discards them unconditionally. Any values are accepted,
including sending both fields together, and neither field imposes an output
limit. Responses `max_output_tokens` remains rejected as an unsupported
parameter.

## Streaming follows each API's native framing

Responses streaming emits typed events such as:

```text
response.created
response.in_progress
response.output_item.added
response.content_part.added
response.output_text.delta
response.output_text.done
response.content_part.done
response.output_item.done
response.completed
```

Each event includes a monotonic `sequence_number`. Terminal failures use
`response.failed`, `response.cancelled`, or `response.incomplete` as
appropriate.

Chat Completions emits `chat.completion.chunk` data frames, an optional
usage-only chunk when `stream_options.include_usage` is true, and a final
`data: [DONE]` marker.

Closing a client connection does not cancel a stored response. Use
`POST /v1/responses/{responseId}/cancel` when cancellation is intended.

## Response chaining reconstructs persisted history

When a request supplies `previous_response_id`, the broker:

1. verifies that every ancestor belongs to the binding's owner scope;
2. rejects missing, non-Responses, incomplete, cyclic, or excessively deep
   chains;
3. reconstructs canonical input and raw compatible output in chronological
   order; and
4. checks for an eligible retained tool execution; on a miss, injects that
   history with app-server `thread/inject_items` before starting a new turn.

The client receives the requested model name, while the mapped Codex model id is
kept in private broker execution metadata.

Normalized image items are persisted with the response just like text items.
`GET /v1/responses/{responseId}/input_items` returns them, and a subsequent
`previous_response_id` request replays them as part of the retained history.

## Unsupported semantics fail instead of changing behavior

The broker rejects fields it cannot honor exactly:

- `tool_choice: "required"` or a named function, `parallel_tool_calls: false`,
  `strict: true` functions, and tool types other than `function`
- `store: false` and response deletion
- temperature, top-p, penalties, logprobs, seed, and token bias
- audio, files, remote input, and other unsupported non-text content
- background or deferred execution
- unknown fields whose behavior could affect output or persistence

These requests return an OpenAI-shaped `400` error with
`code: "unsupported_parameter"` or `code: "invalid_parameter"`. They are never
silently ignored.

## Reviewed bundle tools remain deployment policy

A compatibility binding may select a reviewed broker bundle containing Codex
skills, MCP servers, or broker-hosted tools. Those capabilities are assigned by
the operator and remain governed by bundle, workspace, sandbox, and host
authorization policy.

They are separate from caller-defined OpenAI functions. Sending `tools` never
grants or selects bundle capabilities; see
[Built-in Codex tools are off unless a bundle allows them](#built-in-codex-tools-are-off-unless-a-bundle-allows-them).

## Errors preserve the OpenAI envelope without exposing internals

Authentication, validation, not-found, conflict, and server errors use:

```json
{
  "error": {
    "message": "Reader-safe explanation",
    "type": "invalid_request_error",
    "param": "field_name",
    "code": "unsupported_parameter"
  }
}
```

Terminal Codex failures include the upstream message, for example,
`The completion failed: Selected model is at capacity. Please try a different model.`
If no message is available, chat completions return `The completion failed.`
Only the message text is included; administrator diagnostics, additional error
details, credentials, and account identifiers are excluded or redacted.

For non-streaming chat completions, recognized capacity and overload failures
return HTTP `503` with type `server_error` and code `server_busy`; rate limits
return HTTP `429` with type `rate_limit_error` and code `rate_limit_exceeded`.
Unclassified failures retain HTTP `500` and `server_error`. Streaming chat
completions have already sent HTTP `200`, so their final SSE error carries the
same message, type, and code. Responses retain their failed response object
(HTTP `200`, or a `response.failed` stream event), with the upstream reason in
`error.message` prefixed by `The response failed:`. Recognized capacity and
overload failures use `server_error`; rate limits use `rate_limit_exceeded`.
Without a reason, the message remains `The response failed.`

Common checks:

| Symptom | Check |
| --- | --- |
| `401 invalid_api_key` | Confirm that the client uses the raw compatibility key and that its digest exists in the binding file. |
| `404 model_not_found` | Call `GET /v1/models` with the same key and verify the direct model or alias. |
| `404 resource_not_found` | Confirm that the response id belongs to the same owner binding and was created through `/v1/responses`. |
| `400 unsupported_parameter` | Remove fields outside the documented compatibility subset. |
| `502 app_server_error` | Check broker readiness, Codex authentication, and app-server logs. |

For native owner-scoped APIs, continue with [Host integration](host-integration.mdx)
and [HTTP flow](http-flow.mdx).
