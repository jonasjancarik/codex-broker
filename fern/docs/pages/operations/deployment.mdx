# Deployment

Codex Broker is shipped as an internal Docker image that a host app runs next to its backend or worker services. In most deployments, it is one service inside the host app's existing Docker Compose project, not a separate public stack.

## Image

The Dockerfile installs the official Codex CLI Linux musl release from `openai/codex` and then installs the broker Python package.

Build-time args:

| Arg | Default | Description |
| --- | --- | --- |
| `CODEX_VERSION` | `0.151.0` | Codex CLI release version without the `rust-v` prefix. |
| `TARGETARCH` | supplied by BuildKit | `amd64` maps to `x86_64`; `arm64` maps to `aarch64`. |

GitHub Actions publishes multi-architecture images to `ghcr.io/jonasjancarik/codex-broker`. Pushes to `main` publish `edge`, and `v*` tags publish both `latest` and the matching version tag. Pull requests build the image without pushing it.

## Extend the broker image

Build a derived image when Codex needs extra OS packages, language runtimes, native libraries, OCR data, or common CLI tools inside the broker container.

Example `.codex-broker/Dockerfile`:

```dockerfile
ARG CODEX_BROKER_IMAGE=ghcr.io/jonasjancarik/codex-broker:edge
FROM ${CODEX_BROKER_IMAGE}

USER root
RUN apt-get update \
    && apt-get install -y --no-install-recommends nodejs npm ripgrep \
    && rm -rf /var/lib/apt/lists/*

USER broker
```

Example Compose service:

```yaml
services:
  codex-broker:
    build:
      context: .
      dockerfile: .codex-broker/Dockerfile
      args:
        CODEX_BROKER_IMAGE: ghcr.io/jonasjancarik/codex-broker:edge
    image: my-app-codex-broker:local
```

Prefer build-time installs over startup install scripts. For production, publish the derived image and pull it from the target host instead of rebuilding during every deploy.

## Docker mounts

Use one persistent `/data` volume for broker SQLite state, auth homes, inline bundles, and overlays.

Mount:

- host workspaces under `/workspaces`
- reviewed bundles under `/bundles`
- host-owned job data under a separate path such as `/host-data`

The example Compose file is a broker service slice. Copy its service, volumes, secrets, and mounts into the host app's Compose stack, then point the host backend at `http://codex-broker:3400` on the Compose network.

The broker should usually expose `3400` only to the Compose network. Add a local override with `ports: ["3400:3400"]` only when host-machine access is intentional.

When enabling the example chat bundle, the broker container must share a Docker network or route with the host app service named by the bundle endpoint, currently:

```text
http://app:3000/internal/codex/tools/evidence-search
```

Set `CODEX_HOST_TOOL_KEY` in both the broker process and the host app.

## Secrets

Set `CODEX_BROKER_INTERNAL_KEY_FILE` to a Docker secret path. The broker reports not-ready without an internal key unless `CODEX_BROKER_ALLOW_UNAUTHENTICATED=true` is set for local development.

Deployments that expose the OpenAI-compatible API should mount a second,
read-only secret file and point
`CODEX_BROKER_OPENAI_COMPAT_BINDINGS_FILE` at it:

```yaml
services:
  codex-broker:
    environment:
      CODEX_BROKER_OPENAI_COMPAT_BINDINGS_FILE: /run/secrets/openai_compat_bindings
    secrets:
      - codex_broker_key
      - openai_compat_bindings

secrets:
  codex_broker_key:
    file: ./secrets/codex_broker_key
  openai_compat_bindings:
    file: ./secrets/openai_compat_bindings.json
```

The binding file stores only SHA-256 key digests and fixed caller policy. Store
and distribute each raw compatibility key separately. Compatibility keys,
internal broker keys, and upstream Codex credentials serve different trust
boundaries and should not be reused.

If an operator intentionally enables `danger-full-access`, mount one more
deployment-only secret and set `CODEX_BROKER_DANGER_FULL_ACCESS_KEY_FILE` to
its path. A regular authenticated request must also include that value in
`X-Codex-Broker-Danger-Full-Access-Key`; do not distribute this key to browser
clients or ordinary workload callers.

Do not pass auth files, API keys, or access tokens as bundle content. Codex credentials are stored under hashed auth-principal/profile paths in `/data/auth`.

Codex app-server children start with a scrubbed process environment. Secret-looking variables are not passed through by default. If a reviewed deployment needs a helper inside Codex to read specific environment variables, set `CODEX_BROKER_PASSTHROUGH_ENV` to exact variable names:

```env
CODEX_BROKER_PASSTHROUGH_ENV=ESTF_ARCHIVER_API_URL,ESTF_ARCHIVER_API_KEY
```

## Configuration profiles

Set `CODEX_BROKER_CONFIG_PROFILES_JSON` or `CODEX_BROKER_CONFIG_PROFILES_FILE` to define named runtime and policy profiles. API requests select one with `configProfile`.

Set `CODEX_BROKER_AUTH_PRINCIPAL_MAP_JSON` or `CODEX_BROKER_AUTH_PRINCIPAL_MAP_FILE` to define trusted owner-to-Codex-account mappings. A request `authPrincipalId` must match this policy. Keep the broker key and identity mapping behind the host backend; browser clients must not select either identity directly.

Profiles can set app-server defaults such as `model`, `approvalPolicy`, `sandbox`, `personality`, `serviceTier`, `effort`, `summary`, `webSearch`, `modelVerbosity`, and `imageGeneration`, plus policy fields such as `enabledBundles` and `allowedWorkspaceRoots`.

When profiles are configured, unknown `configProfile` values are rejected.

Compatibility bindings may select one of these configuration profiles plus an
optional reviewed bundle and workspace. The client cannot override those
choices. See [OpenAI compatibility](../integrations/openai-compatibility.mdx)
and [Configuration reference](configuration-reference.mdx#openai-compatible-identity-bindings).

## Readiness

`GET /readyz` checks:

- SQLite state store access
- Codex binary presence
- configured workspace roots are readable/searchable directories
- configured bundle roots are readable/searchable directories
- auth data directory writability
- internal API key presence unless unauthenticated development mode is enabled
- the cached real managed-sandbox preflight result

The preflight starts pinned Codex App Server without a model request, then runs
`command/exec` with the broker-managed workspace permission profile. It proves
that the command can write its temporary workspace and cannot read a protected
canary. Pinned Codex `0.151.0` uses the command `cwd` as this canary's runtime
workspace root; it does not expose `runtimeWorkspaceRoots` on `command/exec`.

`CODEX_BROKER_SANDBOX_PREFLIGHT=required` is the Linux default. A failed or
unsupported result makes readiness return `503` and rejects managed
`read-only` and `workspace-write` turns before model contact. `warn` reports
the result but keeps readiness available; `disabled` reports that the check was
skipped. The probe runs once per broker process rather than on every readiness
request.

Compatibility bindings are optional, so readiness does not require their file.
If `CODEX_BROKER_OPENAI_COMPAT_BINDINGS_FILE` is configured, a missing, empty,
or malformed file fails broker startup instead of silently disabling the
compatible API.

## Managed sandbox requirements

The managed Codex profiles depend on Bubblewrap being able to create Linux user
and PID namespaces. Docker's default seccomp profile can deny the required
namespace setup even when the image and generated Codex configuration are
otherwise valid. Use the shipped
[`examples/seccomp/codex-broker.json`](../../../../examples/seccomp/codex-broker.json)
profile for managed deployments. It is derived from Docker Engine 29.4.0's
pinned Moby seccomp v0.1.0 default profile and narrows its additions to the
Bubblewrap operations exercised by the real canary: mount and `pivot_root`,
`umount2` with `MNT_DETACH`, `clone` calls containing `CLONE_NEWUSER`, and
exact `unshare(CLONE_NEWUSER)` or `unshare(CLONE_NEWNS)` calls.

The example Compose service supplies both
`no-new-privileges:true` and `seccomp=./seccomp/codex-broker.json`. Validate
the resolved configuration before starting it:

```bash
docker compose -f examples/docker-compose.yml config
docker compose -f examples/docker-compose.yml up -d
```

On Docker hosts with AppArmor, Docker's default profile denies the nested mount
operations Bubblewrap needs even when seccomp allows the corresponding
syscalls. Load the shipped profile and add the AppArmor Compose overlay:

```bash
sudo apparmor_parser -r -W examples/apparmor/codex-broker-bwrap
docker compose \
  -f examples/docker-compose.yml \
  -f examples/docker-compose.apparmor.yml \
  config
docker compose \
  -f examples/docker-compose.yml \
  -f examples/docker-compose.apparmor.yml \
  up -d
```

The profile is derived from Moby v28.0.4's `docker-default` template. It keeps
the template's `/proc`, `/sys`, signal, and ptrace restrictions while allowing
the user namespace, mount, unmount, and pivot-root operations covered by the
real canary. Hosts without AppArmor should use only the base Compose file.

Codex 0.151's bundled Bubblewrap reports restrictive-container procfs failures
using wording its built-in fallback does not yet recognize. The broker therefore
uses the supported `--no-proc` fallback: PID isolation and the filesystem
sandbox remain active, while the fresh procfs mount is omitted.

CI is configured to run the no-model sandbox canary with the same profile
before image publication:

```bash
docker run --rm \
  --network none \
  --read-only \
  --security-opt no-new-privileges:true \
  --security-opt apparmor=codex-broker-bwrap \
  --security-opt seccomp=examples/seccomp/codex-broker.json \
  --tmpfs /tmp:rw,nosuid,nodev,noexec,uid=1000,gid=1000,mode=1777 \
  --tmpfs /data:rw,nosuid,nodev,uid=1000,gid=1000,mode=0700 \
  --tmpfs /workspaces:rw,nosuid,nodev,uid=1000,gid=1000,mode=0755 \
  --tmpfs /bundles:rw,nosuid,nodev,uid=1000,gid=1000,mode=0755 \
  -e CODEX_BROKER_ALLOW_UNAUTHENTICATED=1 \
  codex-broker:sandbox-canary \
  python -m codex_broker.sandbox_probe
```

Do not work around this with `seccomp=unconfined`, `apparmor=unconfined`,
privileged containers, or `CAP_SYS_ADMIN`: each discards the least-privilege
outer-container boundary the broker relies on. Keep both host profiles pinned
and re-run the real preflight whenever the Docker Engine baseline, profiles,
Bubblewrap, or Codex version changes.

`approvalsReviewer: auto_review` is not a sandbox backend. It reviews eligible
explicit permission requests under the broker's granular approval policy,
which keeps `sandbox_approval` disabled; it cannot make a failed Bubblewrap
boundary safe. Likewise, separately authorized `danger-full-access` bypasses
the managed filesystem isolation and must be reserved for trusted operational
work.

If credentials may have appeared in model, tool, event, or API output before
safe sanitization was enabled, rotate the affected credentials. Treat output
retention and downstream logs as potentially exposed until that rotation is
complete.

## Process lifecycle

- App Server children start lazily. The pool key uses auth-principal hash, profile, fingerprint, config profile, Codex command/version, credential-store mode, and process config. Compatible no-MCP children may be shared; mounted MCP processes remain owner-isolated.
- Idle children close after `CODEX_BROKER_POOL_IDLE_TTL_SECONDS`.
- Turns using broker-hosted adapters close their app-server child after finalization because adapter config is tied to the turn overlay.
- If a child crashes, its active turns fail and the pool starts a new child for later work.

## Restart and shutdown

- On startup, the broker marks abandoned `starting`, `queued`, and `running` turns failed.
- Pending interactions are marked failed with fallback responses during restart recovery.
- During shutdown, `interrupt` interrupts active turns.
- With `drain`, the broker rejects new turns, waits for accepted work, then interrupts leftovers.

## Observability

- `/metrics` includes in-memory counters, HTTP request counts/durations, SSE disconnects, turn durations, auth counters, and audit-derived counters.
- Runtime Codex auth refresh failures are classified as `codex_auth_requires_admin`.
- Missing Codex rollout/session failures are classified as `session_not_resumable`.
- Structured JSON logs are enabled by default with `CODEX_BROKER_JSON_LOGS=true`.
