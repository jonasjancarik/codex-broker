# Deployment

Codex Broker is shipped as an internal Docker image that a host app runs next to its backend or worker services. In most deployments, it is one service inside the host app's existing Docker Compose project, not a separate public stack.

## Image

The Dockerfile installs the official Codex CLI Linux musl release from `openai/codex` and then installs the broker Python package.

Build-time args:

| Arg | Default | Description |
| --- | --- | --- |
| `CODEX_VERSION` | `0.155.1` | Codex CLI release version without the `rust-v` prefix. |
| `TARGETARCH` | supplied by BuildKit | `amd64` maps to `x86_64`; `arm64` maps to `aarch64`. |

GitHub Actions publishes multi-architecture images to `ghcr.io/jonasjancarik/codex-broker`. Pushes to `main` publish `edge`, and `v*` tags publish both `latest` and the matching version tag. Pull requests build the image without pushing it.

## Extend the broker image

Build a derived image when Codex needs extra OS packages, language runtimes, native libraries, OCR data, or common CLI tools inside the broker container.

Example `.codex-broker/Dockerfile`:

```dockerfile
ARG CODEX_BROKER_IMAGE=ghcr.io/jonasjancarik/codex-broker:edge
FROM ${CODEX_BROKER_IMAGE}

USER root
RUN apt-get update \
    && apt-get install -y --no-install-recommends nodejs npm ripgrep \
    && rm -rf /var/lib/apt/lists/*

USER broker
```

Example Compose service:

```yaml
services:
  codex-broker:
    build:
      context: .
      dockerfile: .codex-broker/Dockerfile
      args:
        CODEX_BROKER_IMAGE: ghcr.io/jonasjancarik/codex-broker:edge
    image: my-app-codex-broker:local
```

Prefer build-time installs over startup install scripts. For production, publish the derived image and pull it from the target host instead of rebuilding during every deploy.

## Docker mounts

Use one persistent `/data` volume for broker SQLite state, auth homes, inline bundles, and overlays.

Mount:

- host workspaces under `/workspaces`
- reviewed bundles under `/bundles`
- host-owned job data under a separate path such as `/host-data`

The example Compose file is a broker service slice. Copy its service, volumes, secrets, and mounts into the host app's Compose stack, then point the host backend at `http://codex-broker:3400` on the Compose network.

The broker should usually expose `3400` only to the Compose network. The local
example binds it to `127.0.0.1:3400`; do not publish it on every host interface
unless a reverse proxy and the host application's authentication model require
that exposure.

When enabling the example chat bundle, the broker container must share a Docker network or route with the host app service named by the bundle endpoint, currently:

```text
http://app:3000/internal/codex/tools/evidence-search
```

Set `CODEX_HOST_TOOL_KEY` in both the broker process and the host app.

## Secrets

Set `CODEX_BROKER_INTERNAL_KEY_FILE` to a Docker secret path. The broker reports not-ready without an internal key unless `CODEX_BROKER_ALLOW_UNAUTHENTICATED=true` is set for local development.

Deployments that expose the OpenAI-compatible API should mount a second,
read-only secret file and point
`CODEX_BROKER_OPENAI_COMPAT_BINDINGS_FILE` at it:

```yaml
services:
  codex-broker:
    environment:
      CODEX_BROKER_OPENAI_COMPAT_BINDINGS_FILE: /run/secrets/openai_compat_bindings
    secrets:
      - codex_broker_key
      - openai_compat_bindings

secrets:
  codex_broker_key:
    file: ./secrets/codex_broker_key
  openai_compat_bindings:
    file: ./secrets/openai_compat_bindings.json
```

The binding file stores only SHA-256 key digests and fixed caller policy. Store
and distribute each raw compatibility key separately. Compatibility keys,
internal broker keys, and upstream Codex credentials serve different trust
boundaries and should not be reused.

If an operator intentionally enables `danger-full-access`, mount one more
deployment-only secret and set `CODEX_BROKER_DANGER_FULL_ACCESS_KEY_FILE` to
its path. A regular authenticated request must also include that value in
`X-Codex-Broker-Danger-Full-Access-Key`; do not distribute this key to browser
clients or ordinary workload callers.

Do not pass auth files, API keys, or access tokens as bundle content. Codex credentials are stored under hashed auth-principal/profile paths in `/data/auth`.

Codex app-server children start with a scrubbed process environment. Secret-looking variables are not passed through by default. If a reviewed deployment needs a helper inside Codex to read specific environment variables, set `CODEX_BROKER_PASSTHROUGH_ENV` to exact variable names:

```env
CODEX_BROKER_PASSTHROUGH_ENV=ESTF_ARCHIVER_API_URL,ESTF_ARCHIVER_API_KEY
```

## Configuration profiles

Set `CODEX_BROKER_CONFIG_PROFILES_JSON` or `CODEX_BROKER_CONFIG_PROFILES_FILE` to define named runtime and policy profiles. API requests select one with `configProfile`.

Set `CODEX_BROKER_AUTH_PRINCIPAL_MAP_JSON` or `CODEX_BROKER_AUTH_PRINCIPAL_MAP_FILE` to define trusted owner-to-Codex-account mappings. A request `authPrincipalId` must match this policy. Keep the broker key and identity mapping behind the host backend; browser clients must not select either identity directly.

Profiles can set app-server defaults such as `model`, `approvalPolicy`, `sandbox`, `personality`, `serviceTier`, `effort`, `summary`, `webSearch`, `modelVerbosity`, and `imageGeneration`, plus policy fields such as `enabledBundles` and `allowedWorkspaceRoots`.

When profiles are configured, unknown `configProfile` values are rejected.

Compatibility bindings may select one of these configuration profiles plus an
optional reviewed bundle and workspace. The client cannot override those
choices. See [OpenAI compatibility](../integrations/openai-compatibility.mdx)
and [Configuration reference](configuration-reference.mdx#openai-compatible-identity-bindings).

## Readiness

`GET /readyz` checks:

- SQLite state store access
- Codex binary presence
- configured workspace roots are readable/searchable directories
- configured bundle roots are readable/searchable directories
- auth data directory writability
- internal API key presence unless unauthenticated development mode is enabled
- the cached real managed-sandbox preflight result

The preflight starts pinned Codex App Server without a model request, then runs
`command/exec` with the broker-managed workspace permission profile. It proves
that the command can write its temporary workspace and cannot read a protected
canary. Pinned Codex `0.155.1` uses the command `cwd` as this canary's runtime
workspace root; it does not expose `runtimeWorkspaceRoots` on `command/exec`.

`CODEX_BROKER_SANDBOX_PREFLIGHT=required` is the Linux default. A failed or
unsupported startup result aborts the broker before it starts serving requests.
If sandbox health becomes invalid while the broker is running, readiness
returns `503` and managed `read-only` and `workspace-write` turns are rejected
before model contact. `warn` reports
the result but keeps readiness available; `disabled` reports that the check was
skipped. The probe runs once per broker process rather than on every readiness
request.

Compatibility bindings are optional, so readiness does not require their file.
If `CODEX_BROKER_OPENAI_COMPAT_BINDINGS_FILE` is configured, a missing, empty,
or malformed file fails broker startup instead of silently disabling the
compatible API.

## Managed sandbox requirements

The managed Codex profiles depend on Bubblewrap being able to create Linux user
and PID namespaces. Docker's default seccomp profile can deny the required
namespace setup, and Docker's default AppArmor policy can deny Bubblewrap's
nested mount operations. The shipped seccomp JSON filters Linux system calls:
it permits the operations needed to create the sandbox while retaining the
other restrictions described below. `no-new-privileges:true` prevents a process
from gaining privileges through execution of another program.

### Where Docker reads security profiles

Docker selects these policies before the container starts, but they have
different setup requirements:

| Setting | Where it is read or loaded |
| --- | --- |
| `docker run --security-opt seccomp=FILE` | The Docker CLI reads JSON on the client machine, relative to the shell's current directory unless the path is absolute, and sends the contents to the daemon. |
| Compose `security_opt: [seccomp=FILE]` | Compose reads JSON on the client, relative to the project directory: normally the directory of the first `-f` file, or the directory selected by `--project-directory`. Absolute paths remain absolute. |
| `apparmor=codex-broker-bwrap` | This names a policy already loaded in the Linux kernel on the Docker daemon host. It is not a JSON file for the client to upload. |

This holds when the daemon runs in an OrbStack or Docker Desktop Linux VM, or
on a remote Linux host. Putting seccomp JSON only in the image, mounting it
inside the container, or copying it only into the VM does not satisfy the
client's file lookup. A checked-in file on the Mac is sufficient for that
lookup; the VM still needs to support the requested sandbox operations.

The client-side reads are explicit in Docker CLI's
[`parseSecurityOpts`](https://github.com/docker/cli/blob/v29.4.0/cli/command/container/opts.go#L879-L909)
and Compose's
[`parseSecurityOpts`](https://github.com/docker/compose/blob/v5.1.2/pkg/compose/create.go#L431-L465).
See also Docker's [Compose path rules](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/)
and [AppArmor guide](https://docs.docker.com/engine/security/apparmor/).

### Local macOS development

Start OrbStack or Docker Desktop and use Docker Compose **2.24.4 or later**.
Run from the repository root:

```bash
docker context show
docker compose version
docker info --format '{{json .SecurityOptions}}'
test -r examples/seccomp/codex-broker.json
docker compose -p codex-broker-local \
  -f examples/docker-compose.yml \
  -f examples/docker-compose.macos.yml \
  -f examples/docker-compose.local.yml \
  config
docker compose -p codex-broker-local \
  -f examples/docker-compose.yml \
  -f examples/docker-compose.macos.yml \
  -f examples/docker-compose.local.yml \
  up --build -d --wait codex-broker
curl --fail http://127.0.0.1:3400/readyz
```

The example uses a development key from `examples/secrets/` and only publishes
the loopback port. Replace that key before using the service outside local
development. Keep the same project name and file list for subsequent Compose
commands, such as `logs --tail=100 codex-broker`.

The macOS overlay contains:

```yaml
services:
  codex-broker:
    security_opt: !override
      - no-new-privileges:true
      - seccomp=./seccomp/codex-broker.json
```

[`!override`](https://docs.docker.com/reference/compose-file/merge/#replace-value)
requires Compose 2.24.4 or later and replaces the complete list. Without it,
merging security options can retain both seccomp entries and still try to open
the missing `/etc` file. Check that `config` shows exactly the two options
above. The first Compose file is in `examples/`, so this seccomp path points to
`examples/seccomp/codex-broker.json`, even when the command runs elsewhere.
When adapting the overlay to another app, use a path relative to that app's
first Compose file (or an absolute client path), and retain any other required
security options in the replacement list. `config` checks the merge; it does
not prove that the JSON can be opened at container creation or that the
sandbox can run.

The `.local.yml` file remains a port-only overlay for either platform. Use the
macOS overlay without the AppArmor overlay; it does not install or disable
AppArmor. If your selected engine reports AppArmor support, use the Linux
profile setup below on its daemon host instead of dropping that protection.
No host security installer is needed for the macOS seccomp path.

OrbStack uses the [`orbstack` context](https://docs.orbstack.dev/docker/#docker-context-socket);
Docker Desktop normally uses `desktop-linux`. Confirm the selected engine
before running the commands. Both use the same client-side seccomp lookup,
but their VM kernels and runtimes can differ. Docker Desktop's optional
[Enhanced Container Isolation](https://docs.docker.com/enterprise/security/hardened-desktop/enhanced-container-isolation/)
uses the Sysbox runtime and user namespaces, so a result on OrbStack does not
establish compatibility with that configuration. Keep those protections
enabled and run the no-model check below on your selected engine. If it
fails, use a supported Linux deployment; do not bypass the sandbox preflight.

### Missing seccomp file

```text
opening seccomp profile (/etc/codex-broker/security/v1/seccomp.json) failed:
open /etc/codex-broker/security/v1/seccomp.json: no such file or directory
```

This means the client cannot open the production seccomp path. On macOS,
include `docker-compose.macos.yml` as shown above and verify the resolved list
no longer contains `/etc/codex-broker/security/v1/seccomp.json`. On Linux with
the client and daemon on the same host, run the installer below. For a remote
context, make the JSON available on the client or point Compose at a readable
client copy. Rebuilding the image alone cannot fix this error.

### Linux host setup

Run the commands below from the repository root. The example build pins the
same Codex version as the Dockerfile; release tests check that they agree.

The repository ships an idempotent installer. Run its non-mutating check on a
new host or before every deployment, then run it with `sudo` once to install or
update the root-owned profiles:

```bash
./scripts/install-host-security-profiles.sh --dry-run
sudo ./scripts/install-host-security-profiles.sh
sudo ./scripts/install-host-security-profiles.sh --check
```

These commands assume the Docker client and daemon run on the same Linux host.
The installer copies seccomp JSON for the client and loads AppArmor in that
host's kernel. With a remote client, also provide a client-readable seccomp
file. Running the installer on macOS or Windows cannot load an AppArmor policy
into a remote daemon host or Linux VM.

It verifies the repository profile checksums and syntax, installs the seccomp
policy at `/etc/codex-broker/security/v1/seccomp.json`, installs the AppArmor
policy at `/etc/apparmor.d/codex-broker-bwrap`, and loads the AppArmor policy
when AppArmor is enabled. The AppArmor file is persistent, so the profile is
available after a host reboot. Re-run the check after reboot before recreating
the broker container; a missing loaded profile makes Docker reject the
container at creation time. A non-root `--check` that cannot read the kernel's
loaded-profile list fails and tells the operator to re-run it with `sudo`; it
never treats an unreadable AppArmor status as AppArmor being disabled.

The base Compose service supplies `no-new-privileges:true` and references the
stable seccomp path. On hosts with AppArmor enabled, add the AppArmor overlay:

```bash
docker compose \
  -f examples/docker-compose.yml \
  -f examples/docker-compose.apparmor.yml \
  config
docker compose \
  -f examples/docker-compose.yml \
  -f examples/docker-compose.apparmor.yml \
  up -d
```

Hosts without AppArmor use the base file alone, but must still install the
seccomp policy. Do not add the AppArmor overlay when `aa-status` reports that
AppArmor is disabled or unavailable. Do not substitute `apparmor=unconfined`,
`seccomp=unconfined`, privileged mode, or `CAP_SYS_ADMIN`; those remove the
outer container protections rather than fixing the configuration.

The checked-in policies identify their exact Moby source tags and source
checksums. Seccomp blocks direct `AF_ALG` and `AF_VSOCK` sockets and returns
`ENOSYS` for the legacy `socketcall` multiplexer, because seccomp cannot inspect
the address family behind that syscall's userspace pointer. The image supports
only 64-bit amd64 and arm64 userlands, so this deliberate legacy-syscall denial
does not affect a supported image architecture. AppArmor also denies `AF_ALG`
as an LSM defense. The only other seccomp deviations are Bubblewrap operations
the real canary exercises: mount and `pivot_root`, `umount2(MNT_DETACH)`, user
namespace clones, and exact user or mount namespace `unshare` calls. The
AppArmor policy preserves Moby's `/proc`, `/sys`, network, signal, and ptrace
restrictions while allowing only Bubblewrap's user namespace, mount, unmount,
and pivot-root operations.

On systemd hosts, check `systemctl status apparmor.service` and
`systemctl is-enabled apparmor.service`; ensure the distribution's profile
loader runs before Docker restores containers at boot. After a host reboot,
confirm `sudo aa-status` lists `codex-broker-bwrap` in enforce mode and check
broker readiness again. Loading a file directly from the checkout with
`apparmor_parser` alone does not install it for future boots. See
[Ubuntu's AppArmor administration guide](https://ubuntu.com/server/docs/how-to/security/apparmor/)
for host profile management.

When integrating into an app's Compose stack, add
`apparmor=codex-broker-bwrap` alongside its existing `no-new-privileges:true`
and seccomp settings. Keep all three settings in the resolved configuration.

### Verify the running container and diagnose sandbox failures

For the example AppArmor stack, inspect the active profile and broker response:

```bash
docker compose -f examples/docker-compose.yml -f examples/docker-compose.apparmor.yml \
  exec codex-broker cat /proc/self/attr/current
docker compose -f examples/docker-compose.yml -f examples/docker-compose.apparmor.yml \
  exec codex-broker curl -sS http://127.0.0.1:3400/readyz
docker compose -f examples/docker-compose.yml -f examples/docker-compose.apparmor.yml \
  logs --tail=100 codex-broker
```

Expect `codex-broker-bwrap (enforce)` and a successful readiness result. Use
your app's Compose files and service name when integrating these checks.

If Docker reports the named AppArmor profile is missing, rerun the installer
on the Linux daemon host and confirm
`sudo ./scripts/install-host-security-profiles.sh --check` succeeds before
retrying. For a missing seccomp file, follow the client-path remedy above.
For namespace or mount permission errors, verify the resolved seccomp path and
active AppArmor profile, then inspect `sudo journalctl -k --since "10 minutes ago"`
on the host for AppArmor `DENIED` records. Host policy must permit unprivileged
user namespaces; the container profiles cannot override a host-wide ban.
[Docker's AppArmor guide](https://docs.docker.com/engine/security/apparmor/)
explains profile inspection and denial logs.

After correcting host policy, recreate the broker with the same Compose files
and `up -d --force-recreate codex-broker`. This applies container security
changes and reruns the startup preflight, whose result is cached. Check
`/readyz` before sending work; do not set the preflight to `warn` or `disabled`
to hide a failed production sandbox check.

Codex 0.151's bundled Bubblewrap reports restrictive-container procfs failures
using wording its built-in fallback does not yet recognize. The broker therefore
uses the supported `--no-proc` fallback: PID isolation and the filesystem
sandbox remain active, while the fresh procfs mount is omitted.

CI is configured to validate the profile metadata and run the no-model sandbox
canary with the same profiles before image publication:

```bash
docker run --rm \
  --network none \
  --read-only \
  --security-opt no-new-privileges:true \
  --security-opt apparmor=codex-broker-bwrap \
  --security-opt seccomp=/etc/codex-broker/security/v1/seccomp.json \
  --tmpfs /tmp:rw,nosuid,nodev,noexec,uid=1000,gid=1000,mode=1777 \
  --tmpfs /data:rw,nosuid,nodev,uid=1000,gid=1000,mode=0700 \
  --tmpfs /workspaces:rw,nosuid,nodev,uid=1000,gid=1000,mode=0755 \
  --tmpfs /bundles:rw,nosuid,nodev,uid=1000,gid=1000,mode=0755 \
  -e CODEX_BROKER_ALLOW_UNAUTHENTICATED=1 \
  codex-broker:sandbox-canary \
  python -m codex_broker.sandbox_probe
```

For an isolated macOS check, build from the repository root and use the
client-side profile directly. This starts no service, publishes no port,
mounts no host credentials or persistent data, and makes no model request:

```bash
docker build -t codex-broker:local .
docker run --rm \
  --network none \
  --read-only \
  --security-opt no-new-privileges:true \
  --security-opt seccomp=./examples/seccomp/codex-broker.json \
  --tmpfs /tmp:rw,nosuid,nodev,noexec,uid=1000,gid=1000,mode=1777 \
  --tmpfs /data:rw,nosuid,nodev,uid=1000,gid=1000,mode=0700 \
  --tmpfs /workspaces:rw,nosuid,nodev,uid=1000,gid=1000,mode=0755 \
  --tmpfs /bundles:rw,nosuid,nodev,uid=1000,gid=1000,mode=0755 \
  -e CODEX_BROKER_ALLOW_UNAUTHENTICATED=1 \
  codex-broker:local \
  python -m codex_broker.sandbox_probe
```

Expect exit status zero and `"status": "healthy"`. A namespace, mount, or
procfs error after container creation is a separate runtime limitation from
the missing-file error. Keep the seccomp filter, `no-new-privileges`, and
required startup preflight enabled while diagnosing it.

Validation on 2026-09-22: the no-model check passed on Apple Silicon with
OrbStack 2.2.3, Docker Engine/CLI 29.4.0, Compose 5.1.2, and the checkout's
Codex 0.155.0 image. That daemon reported seccomp support and no AppArmor
support. Both the Linux and macOS Compose configurations were resolved and
checked. A separate disposable Compose service using the macOS overlay also
passed the probe and reported `NoNewPrivs: 1` and `Seccomp: 2`. Docker Desktop,
including Enhanced Container Isolation, was not runtime-tested; its path
guidance above is based on the Docker client source
and documentation. This check does not exercise a model request or the full
host application's integration.

Keep both host profiles pinned and re-run the real preflight whenever the Moby
baseline, profiles, Bubblewrap, or Codex version changes. The profile version
is part of the broker release's deployment contract: upgrade the image and the
installed profile together, run `--check`, then recreate the service.

`approvalsReviewer: auto_review` is not a sandbox backend. It reviews eligible
explicit permission requests under the broker's granular approval policy,
which keeps `sandbox_approval` disabled; it cannot make a failed Bubblewrap
boundary safe. Likewise, separately authorized `danger-full-access` bypasses
the managed filesystem isolation and must be reserved for trusted operational
work.

If credentials may have appeared in model, tool, event, or API output before
safe sanitization was enabled, rotate the affected credentials. Treat output
retention and downstream logs as potentially exposed until that rotation is
complete.

## Process lifecycle

- App Server children start lazily. The pool key uses auth-principal hash, profile, fingerprint, config profile, Codex command/version, credential-store mode, and process config. Compatible no-MCP children may be shared; mounted MCP processes remain owner-isolated.
- Idle children close after `CODEX_BROKER_POOL_IDLE_TTL_SECONDS`.
- Set `CODEX_BROKER_MAX_POOLED_APP_SERVERS` to cap live and starting App Server children. At capacity, the broker evicts the least-recently-used idle child or returns explicit backpressure if every child is active.
- Turns using broker-hosted adapters close their app-server child after finalization because adapter config is tied to the turn overlay.
- If a child crashes, its active turns fail and the pool starts a new child for later work.

One App Server child can consume roughly 100–200 MiB depending on Codex version
and configuration. Measure the container cgroup under representative traffic.
For a small host, start with two active turns, two pooled children, and a
60–120 second idle TTL; add container memory and PID limits with enough room
for both children to start and finish cleanly.

## Restart and shutdown

- In required-preflight mode, the broker aborts startup before opening its state database when the managed sandbox canary is unhealthy. A service manager can then restart or alert instead of leaving an unavailable process running indefinitely.
- After a successful preflight, the broker marks abandoned `starting`, `queued`, and `running` turns failed.
- Pending interactions are marked failed with fallback responses during restart recovery.
- During shutdown, `interrupt` interrupts active turns.
- With `drain`, the broker rejects new turns, waits for accepted work, then interrupts leftovers.

## Observability

- `/metrics` includes in-memory counters, HTTP request counts/durations, SSE disconnects, turn durations, auth counters, and audit-derived counters.
- Runtime Codex auth refresh failures are classified as `codex_auth_requires_admin`.
- Missing Codex rollout/session failures are classified as `session_not_resumable`.
- Structured JSON logs are enabled by default with `CODEX_BROKER_JSON_LOGS=true`.
