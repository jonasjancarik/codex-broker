# App-server modes

This matrix is pinned to the Codex CLI app-server protocol generated from `codex-cli 0.146.0`:

```bash
codex app-server generate-ts --experimental --out /private/tmp/codex-app-server-ts-0.146.0
codex app-server generate-json-schema --experimental --out /private/tmp/codex-app-server-json-schema-0.146.0
```

Compared with `0.144.6`, the `0.146.0` protocol adds `dynamicTools` and
`experimentalRawEvents` to `thread/start` along with new app-server APIs. The
broker-used surfaces below remain compatible and the production no-model
sandbox canary passes with the new binary.

The app-server protocol exposes two collaboration mode kinds in `ModeKind`: `default` and `plan`. Goal tracking, review, approvals, user-input prompts, and MCP elicitations are separate app-server capabilities.

| Capability | 0.146.0 app-server surface | Broker support | Host-facing surface |
| --- | --- | --- | --- |
| Model and selector capabilities | `model/list`, including reasoning efforts, modalities, personality support, service tiers, defaults, visibility, and upgrade metadata | Implemented with auth-principal/profile scoping and pagination | `GET /v1/owners/{ownerId}/auth/models` |
| Default chat/work turns | `thread/start`, `thread/resume`, `turn/start`, `turn/steer`, `turn/interrupt` | Implemented | Thread and turn HTTP APIs; `message.*`, `reasoning.*`, `tool.*`, and `turn.*` events |
| Stable compatible output | `rawResponseItem/completed` | Persisted independently of optional raw-event debugging | `compat.response.output_item`; Responses and Chat Completions output |
| Token usage | `thread/tokenUsage/updated` | Persists and validates exact turn and cumulative thread counts plus the model context window | Native `Turn.usage` and `turn.usage.updated`; OpenAI response and optional Chat stream usage |
| Compatible response history | `thread/inject_items` | Injects validated same-owner `previous_response_id` chains before `turn/start` | Responses `previous_response_id` |
| Caller-defined dynamic tools | `thread/start.dynamicTools`, `DynamicToolSpec`, and server request `item/tool/call` | Not mapped; compatible `tools`, `tool_choice`, tool messages, and function outputs are rejected until the broker implements the full lifecycle | OpenAI-shaped `400 unsupported_parameter` |
| Plan collaboration mode | `ModeKind = "default" \| "plan"`, `ThreadSettings.collaborationMode`, `turn/plan/updated`, `item/plan/delta` | Event normalization implemented | `thread.settings.updated`, `plan.updated`, `plan.delta` events |
| Goal tracking | `thread/goal/set`, `thread/goal/get`, `thread/goal/clear`, `thread/goal/updated`, `thread/goal/cleared` | Event normalization implemented; direct broker goal API not yet implemented | `goal.updated`, `goal.cleared` events |
| Review mode | `review/start`, `enteredReviewMode`, `exitedReviewMode`, auto-approval review notifications | Event normalization implemented; direct broker review API not yet implemented | `review.entered`, `review.exited`, `approval.review.started`, `approval.review.completed` events |
| Tool/file/permission approvals | `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/permissions/requestApproval`, legacy `applyPatchApproval`, `execCommandApproval` | Implemented with pending interaction storage, host resolve API, and safe fallbacks | `tool.requested`, `approval.requested`, `approval.resolved`, interaction APIs, owner audit entries |
| User input prompts | `item/tool/requestUserInput` | Implemented with pending interaction storage, host resolve API, and safe empty-answer fallback | `user_input.requested`, `user_input.resolved`, interaction APIs |
| MCP elicitations | `mcpServer/elicitation/request`; initialize capability `mcpServerOpenaiFormElicitation` | Implemented with pending interaction storage, host resolve API, and safe decline fallback | `mcp.elicitation.requested`, `mcp.elicitation.resolved`, interaction APIs |

## API direction

The broker treats app-server mode-like behavior as observable event state unless there is already a stable product-facing API. Model discovery directly maps `model/list` and preserves every model field for forward compatibility.

Codex 0.146.0 exposes `experimentalRawEvents` on `ThreadStartParams`. The
broker leaves that experimental stream disabled and consumes the declared
`rawResponseItem/completed` notification for stable compatible output.

The generated protocol includes `thread/start.dynamicTools`, `item/tool/call`,
and dynamic-tool result types. Reviewed bundle and MCP tools are deployment
policy, not caller-granted functions, and the broker does not yet map the full
OpenAI declaration, call, result, cancellation, and streaming lifecycle.
Compatible tool semantics therefore remain rejected instead of being only
partially implemented.

The 0.146.0 Linux package does not include the former
`codex-responses-api-proxy` executable. Codex Broker continues to own identity
mapping, scheduling, persistence, and REST/SSE translation over app-server.

Future product APIs should follow these boundaries:

- Plan mode: expose current collaboration state and plan updates from events. Add a setter only if a generated app-server method appears for updating `ThreadSettings.collaborationMode`, or if the broker implements a supported Codex command path for switching modes.
- Model catalog: keep discovery scoped to trusted owner-to-principal policy and the selected profile, with pagination and all advertised service tiers.
- Goal tracking: add broker goal APIs once the broker can safely run `thread/goal/*` methods against a loaded Codex thread outside an active turn.
- Review: add a review API around `review/start` once response and delivery semantics are mapped to broker turn state.
- Approvals, user input, and MCP elicitations: keep pending interaction records, resolve APIs, and fallback response shapes in sync with generated app-server schemas.

The broker must always fall back on timeout or child loss so an app-server child is never left waiting indefinitely for a host UI.

## Updating this matrix

When updating for a new Codex version:

1. Regenerate the TypeScript and JSON schema artifacts.
2. Compare `ModeKind`, `ClientRequest`, `ServerRequest`, and response types.
3. Re-check `rawResponseItem/completed`, `thread/tokenUsage/updated`,
   `thread/inject_items`, and `item/tool/call`.
4. Update event normalization, compatibility fixtures, and interaction
   fallback logic as needed.
5. Update this page in the same change.
