# Architecture

Codex Broker is an internal HTTP service that runs next to a host application. It manages Codex auth homes, `codex app-server` child processes, durable broker thread and turn state, bundle mounting, and normalized event streaming.

## Concrete example

Say a support app has an agent chat that can ask Codex to inspect a customer's account notes and draft a response.

The support app still decides when Codex should run. It authenticates the support agent, checks that the agent may access the customer, builds the product-specific prompt, chooses the `ownerId`, reuses the support conversation id as `threadId`, selects a `bundleId` that exposes the approved evidence-search tool, and sends a turn to the broker.

The broker starts after that decision. It uses the resolved auth-principal/profile home, starts or reuses a `codex app-server` child, maps the broker thread to the underlying Codex thread, prevents another turn from racing on the same support conversation, mounts the bundle, persists normalized events, and streams those events back to the app.

The support app then renders the stream, stores the final draft, and enforces any product review rules. The broker does not decide who the support agent is, which customer records are allowed, or what a good support response looks like.

## Runtime shape

```text
host app backend or worker
  |
  | HTTP JSON requests
  | SSE event stream
  v
codex-broker process
  |
  +-- HTTP API
  |     authenticates native broker keys and OpenAI compatibility keys
  |     exposes health, readiness, OpenAPI, metrics, native APIs, Responses, and Chat Completions
  |
  +-- AuthManager
  |     HMACs owner and auth-principal ids
  |     creates auth-principal/profile CODEX_HOME directories
  |     creates separate non-secret runtime HOME directories for children
  |     runs codex login/status/logout commands
  |
  +-- TurnScheduler
  |     creates broker threads and turns
  |     enforces one active turn per broker thread
  |     runs reject, queue, and steer behavior
  |     normalizes Codex app-server notifications into broker events
  |     gates managed turns on the cached sandbox preflight result
  |
  +-- AppServerPool
  |     starts long-lived codex app-server children
  |     routes JSON-RPC requests, responses, notifications, and server requests
  |     reuses or closes children by pool key
  |
  +-- BundleRegistry
  |     resolves mounted and inline task bundles
  |     validates workspace paths, MCP commands, and hosted-tool endpoints
  |     materializes per-turn overlays
  |
  +-- StateStore
        persists SQLite tables for Codex auth profiles, threads, turns, events,
        bundle digests, app-server processes, audit logs, and interactions
```

The implementation uses the Python standard library HTTP server and `subprocess`. The console entry point is `codex_broker.__main__:main`, which builds `BrokerConfig.from_env()` and starts the HTTP server.

## Startup

On startup, the broker:

1. Reads environment into `BrokerConfig`.
2. Ensures `data_dir`, `auth_root`, `inline_bundle_root`, and `overlay_root` exist.
3. Opens the SQLite state store.
4. Marks abandoned `starting`, `queued`, and `running` turns as failed.
5. Marks pending interactions failed with fallback responses.
6. Prunes persisted raw app-server event fields when raw capture retention is enabled.
7. Builds the secret sanitizer and registers broker control-plane secrets.
8. Constructs native auth, compatibility auth, bundle, app-server pool, and
   scheduler services, then runs the cached managed-sandbox preflight.
9. Starts `ThreadingHTTPServer` on `CODEX_BROKER_HOST:CODEX_BROKER_PORT`.

Only `GET /healthz` and `GET /readyz` are unauthenticated. Native product
routes, `/metrics`, `/openapi.json`, and `/v1/bundles/inline` require the
internal broker key unless `CODEX_BROKER_ALLOW_UNAUTHENTICATED=true`.
OpenAI-compatible routes always require a separately configured compatibility
key whose digest maps to a fixed server-side caller binding.

## Data layout

```text
<data_dir>/
  state/
    broker.sqlite
    owner-hash.key
  auth/
    principals/
      <auth-principal-hash>/
        profiles/
          <profile>/
            codex-home/
              auth.json
              config.toml
  bundles/
    inline/
      <sha256-digest>/
        bundle.json
  workspaces/
    runtime-homes/
      <auth-principal-hash>/profiles/<profile>/
    overlays/
      <turn-id>/
        AGENTS.md
        .agents/skills/<skill-name> -> mounted skill directory
        .codex/config.toml
        prompts/<prompt-name>.<ext> -> mounted prompt file
        tool-adapters.json
```

The default data directory is `.data`; Docker deployments usually set it to `/data`.

## SQLite state

`StateStore` creates tables for:

- auth-principal Codex profiles and auth status
- broker threads
- turns
- normalized events and optional, always-redacted raw app-server fields
- bundle digests
- app-server process diagnostics
- user-scoped audit logs
- pending interactions

Restart recovery is conservative. Turns that were in progress before process death are failed because the app-server child that owned them is gone. Pending interactions are resolved with fallback responses so host UIs do not show stale prompts.

By default, normalization is sanitized before persistence and again when
historical records are read, so existing rows cannot bypass current secret
registration. The same sanitizer runs immediately before native and
OpenAI-compatible output is returned. Trusted debugging can select raw
normalized output, but raw app-server fields and logs stay redacted.

## Compatible responses reuse the scheduler and durable event store

The compatibility façade is an adapter over the same broker runtime rather than
a second execution system:

1. The bearer key resolves an immutable owner/principal/profile/policy binding.
2. The requested model or alias is checked against app-server `model/list`.
3. The broker creates a fresh broker thread and a compatibility-marked turn.
4. A `previous_response_id` chain, when present, is reconstructed from
   owner-scoped persisted records and sent through `thread/inject_items`.
5. The scheduler starts the Codex turn with the binding's bundle, workspace,
   model, reasoning, service-tier, instruction, and output-schema policy.
6. `rawResponseItem/completed` becomes `compat.response.output_item`, while
   `thread/tokenUsage/updated` is retained internally for compatible response
   assembly and exposed to native clients as `Turn.usage` and
   `turn.usage.updated`.
7. Synchronous responses, retrieval, and terminal stream events are assembled
   from those durable records.

Generic message events are useful for live deltas, but they are not treated as
the final compatible response contract. A completed compatible response fails
closed if its stable output item or token usage is missing or malformed.

Every response gets a fresh broker thread so synchronous requests do not share
mutable conversation state accidentally. Continuation is explicit through
`previous_response_id`, and closing an HTTP stream does not implicitly cancel
the persisted turn.

## App-server pool

`AppServerPool` starts children lazily with:

```text
<CODEX_BIN> app-server --listen stdio://
```

The pool uses the profile `codex-home` as `CODEX_HOME` and a separate
non-secret runtime directory as `HOME`. Its key includes auth-principal hash,
Codex auth profile, auth fingerprint, runtime home, `configProfile`, Codex
command/version, credential-store mode, client identity fields, and
process-level Codex config. Compatible children can serve isolated owner
contexts. Mounted MCP declarations add owner scope because an MCP process may
retain tenant state. Explicit unknown upstream thread or turn ids are never
routed by single-context guessing.

`GET /v1/owners/{ownerId}/auth/models` uses the selected principal/profile child to call App Server `model/list`. The broker does not persist the catalog; it preserves advertised reasoning, modality, personality, visibility, upgrade, and service-tier fields in the HTTP response.

Threads persist an immutable principal/profile/profile-instance binding. Deleting a profile changes the instance and fences old or queued work. Databases with a different schema version are rejected rather than migrated.

Idle children are closed after `CODEX_BROKER_POOL_IDLE_TTL_SECONDS`. Closed or crashed children are removed and restarted lazily on later work. Children with active turn contexts are not swept.

Turns that use broker-hosted HTTP adapters close their app-server child after finalization because adapter config includes per-turn overlay context.

## Separate credentials preserve the identity boundary

The broker remains an internal service. Native host integrations use the
internal broker key. OpenAI-compatible clients use separate compatibility keys
that select server-owned identity and policy bindings. Neither credential is
accepted on the other's route set, and neither replaces the upstream Codex
credential stored in the selected auth profile.

Main controls:

- broker-key authentication for product routes
- digest-only compatibility-key authentication with immutable server-side bindings
- strict separation between native, compatibility, and upstream credentials
- owner-scoped broker-state isolation and auth-principal/profile auth-home isolation
- HMAC-derived owner/principal paths and hashes in logs
- scrubbed child process environments
- explicit pass-through environment allowlists
- reviewed bundle roots
- workspace root validation
- MCP command allowlisting
- hosted-tool URL allowlisting
- `env:VAR` indirection for secret-looking headers and MCP environment values
- default-deny managed permission profiles, canonical runtime workspace roots,
  and explicit broker control-plane and credential-path denies
- cached sandbox canary gating for managed work when required by deployment
- safe sanitization on persistence, history reads, and native/OpenAI egress;
  mandatory redaction for logs and raw event persistence

Managed `read-only` and `workspace-write` requests become broker-owned
permission profiles, not caller-provided low-level sandbox settings. They use
`auto_review` and a granular policy that permits reviewed exceptions without
allowing `sandbox_approval` to turn into an unsandboxed shell bypass. A failed
required canary makes `/readyz` unhealthy and rejects managed turns before a
model is contacted. `danger-full-access` is different: a separately configured
per-request key authorizes it, and it does not provide the managed isolation
guarantee.

The cached no-model canary uses `command/exec` with a temporary workspace as
`cwd`. Pinned Codex `0.151.0` has no `runtimeWorkspaceRoots` field on that
command, so `cwd` supplies the canary's runtime workspace root. The broker
continues to send canonicalized `runtimeWorkspaceRoots` on managed thread and
turn calls.

Sanitization is defense in depth. The host app must still avoid placing
credentials intentionally in prompts or input items, because the model receives
those values before any output sanitization occurs.

## Shutdown

On process shutdown, the server stops accepting work and calls scheduler shutdown:

- `CODEX_BROKER_SHUTDOWN_MODE=interrupt` interrupts active turns and finalizes them as interrupted.
- `CODEX_BROKER_SHUTDOWN_MODE=drain` rejects new turns, waits up to `CODEX_BROKER_SHUTDOWN_DRAIN_TIMEOUT_SECONDS`, then interrupts leftovers.

After scheduler shutdown, the pool closes all app-server children and the state store is closed.
