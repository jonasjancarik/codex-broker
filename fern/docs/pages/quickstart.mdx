# Quickstart

Codex Broker is normally added as a service inside the host app's Docker Compose stack. The host backend and workers call it over the Compose network; browser clients keep calling the host app.

This quickstart uses the repo's example Compose files as a standalone local stack. It keeps the same data, workspace, bundle, and secret layout you should copy into a host-app deployment.

## Prerequisites

- Docker with Compose support.
- A checked-out Codex Broker repo.
- Codex credentials or an OpenAI API key when you want real Codex turns.

Python and `uv` are only needed for native development.

For managed `read-only` or `workspace-write` turns, install the repository's
host security profiles before starting Docker. See the [managed sandbox host
setup](operations/deployment.mdx#managed-sandbox-requirements) for the one-time,
persistent setup and release update procedure:

```bash
./scripts/install-host-security-profiles.sh --dry-run
sudo ./scripts/install-host-security-profiles.sh
sudo ./scripts/install-host-security-profiles.sh --check
```

Run this on the Linux machine where the Docker daemon runs. A macOS or Windows
Docker Desktop client is not that host; its Linux VM needs the profiles instead.

If `docker info` reports AppArmor, install and load the AppArmor profile on the
Docker host as described in that guide, then start the local example with its
overlay:

```bash
docker info --format '{{json .SecurityOptions}}'
docker compose \
  -f examples/docker-compose.yml \
  -f examples/docker-compose.apparmor.yml \
  -f examples/docker-compose.local.yml \
  up --build
```

On hosts without AppArmor, use the base and local Compose files shown below.

## Start the local example

Run from the repository root:

```bash
docker compose \
  -f examples/docker-compose.yml \
  -f examples/docker-compose.local.yml \
  up --build
```

`examples/docker-compose.yml` is the broker service slice you would fold into a real app stack. It uses persistent `/data`, reviewed bundles mounted at `/bundles`, a deliberately empty narrow sample workspace mounted under `/workspaces/app`, and the broker key loaded from a Docker secret. Replace that sample with only the individual job or project directory Codex may access; never mount a repository parent or your home directory.

`examples/docker-compose.local.yml` publishes `127.0.0.1:3400` so you can call the broker from your shell while testing.

The example secret file contains the development key used below:

```text
dev-only-key
```

Replace `examples/secrets/codex_broker_key.example` with a real secret file for any shared environment.

## Add it to an app stack

In a real product deployment, copy the `codex-broker` service shape into the app's existing `docker-compose.yml` instead of running this repo's example stack by itself.

Start with this service definition and adjust the workspace and bundle source paths for your app:

```yaml
services:
  codex-broker:
    image: ghcr.io/jonasjancarik/codex-broker:v0.10.2
    read_only: true
    security_opt:
      - no-new-privileges:true
      - seccomp=/etc/codex-broker/security/v1/seccomp.json
      # On AppArmor hosts, add this after installing the profile:
      # - apparmor=codex-broker-bwrap
    tmpfs:
      - /tmp
    volumes:
      - codex-broker-data:/data
      - ./authorized-job:/workspaces/app:rw
      - ./codex-bundles:/bundles:ro
    secrets:
      - codex_broker_key
    restart: unless-stopped

volumes:
  codex-broker-data:

secrets:
  codex_broker_key:
    file: ./secrets/codex_broker_key
```

Pin the image to a specific release tag for reproducible production deployments. The seccomp path above is installed on the Docker host by the deployment setup. On AppArmor hosts, add `apparmor=codex-broker-bwrap` after the profile is installed. Services on the same Compose network can reach the broker at `http://codex-broker:3400` without an `expose` or `ports` entry.

Only publish `3400` to the host machine for local debugging. In production-style Compose stacks, leave the broker on the internal Compose network and have the host app call it server-side.

## Check readiness

Health and readiness:

```bash
curl -sS http://127.0.0.1:3400/healthz
curl -sS http://127.0.0.1:3400/readyz
```

`/readyz` checks the internal key, SQLite state store, Codex binary, configured workspace roots, bundle roots, auth-root writability, and the cached real managed-sandbox preflight result. With the default required preflight, the broker fails to start when the result is unhealthy; if a running broker reports an unhealthy cached result, `/readyz` returns `503` and managed turns are rejected. After fixing a host profile or Compose security option, recreate the broker so startup reruns the preflight, then check `/readyz` again.

## Check user auth

Use a stable product user id or service-account id as `ownerId`:

```bash
BROKER=http://127.0.0.1:3400
BROKER_KEY=dev-only-key
OWNER=service-account-1

curl -sS \
  -H "Authorization: Bearer $BROKER_KEY" \
  "$BROKER/v1/owners/$OWNER/auth/status"
```

`ownerId` owns broker state. Trusted policy resolves the Codex auth principal, defaulting to the same id. Omitting `profile` uses `default`; select it explicitly when creating the broker thread.

For service-account style deployments, store an API key in the service account's Codex auth profile:

```bash
curl -sS \
  -X POST \
  -H "Authorization: Bearer $BROKER_KEY" \
  -H "Content-Type: application/json" \
  -d '{"apiKey":"'"$OPENAI_API_KEY"'"}' \
  "$BROKER/v1/owners/$OWNER/auth/api-key"
```

If you use device auth instead, start and submit the device flow through the auth endpoints. Keep browser login and product UI auth outside the broker.

## Use an OpenAI SDK with a compatibility binding

OpenAI-compatible clients need a separate key binding. Create a random key,
store its SHA-256 digest in a JSON file, and start the broker with
`CODEX_BROKER_OPENAI_COMPAT_BINDINGS_FILE` pointing to that file:

```json
{
  "sha256:<lowercase-hex-digest>": {
    "ownerId": "service-account-1",
    "profile": "default",
    "configProfile": "default",
    "hostApp": "openai-sdk"
  }
}
```

The raw key is distributed to the client, not stored in the binding file. Once
configured, only the base URL and API key change. The built-in `gpt-5.6` alias
resolves to `gpt-5.6-sol`; no alias configuration is needed:

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:3400/v1",
    api_key="the-raw-compatibility-key",
)
response = client.responses.create(
    model="gpt-5.6",
    input="Summarize this repository.",
)
print(response.output_text)
```

This surface supports text and base64 image input in Responses and Chat
Completions, including streaming, retrieval, cancellation, response chaining,
reasoning controls, service tiers, and JSON Schema output. It rejects
caller-defined tools and other fields the broker cannot honor exactly. See
[OpenAI compatibility](integrations/openai-compatibility.mdx) for image formats,
limits, and the token-cap behavior.

Before adapting an existing client, read
[OpenAI compatibility](integrations/openai-compatibility.mdx) for the endpoint
and parameter matrix, streaming behavior, credential separation, and
unsupported semantics.

## Create a thread

```bash
curl -sS \
  -X POST \
  -H "Authorization: Bearer $BROKER_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "threadId": "chat-123",
    "profile": "default",
    "hostApp": "chat-app",
    "bundleId": "example-chat-v1",
    "configProfile": "default",
    "cwd": "/workspaces/app"
  }' \
  "$BROKER/v1/owners/$OWNER/threads"
```

Repeated creates with the same owner and `threadId` return the existing broker thread only when the immutable principal/profile binding matches. To share one Codex account across owners, configure the owner-to-principal mapping on the broker; do not accept it from untrusted browser input.

## Submit a turn

```bash
THREAD_ID=chat-123

curl -sS \
  -X POST \
  -H "Authorization: Bearer $BROKER_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "input": [
      { "type": "text", "text": "Summarize the evidence for this user question." }
    ],
    "hostApp": "chat-app",
    "bundleId": "example-chat-v1",
    "configProfile": "default",
    "mode": "queue",
    "productCorrelationId": "chat-123:message-456",
    "idempotencyKey": "chat-123:message-456"
  }' \
  "$BROKER/v1/owners/$OWNER/threads/$THREAD_ID/turns"
```

The response includes `turnId`, `status`, and a relative `streamUrl`.

## Stream events

```bash
TURN_ID=turn_...

curl -N \
  -H "Authorization: Bearer $BROKER_KEY" \
  "$BROKER/v1/owners/$OWNER/threads/$THREAD_ID/events?turnId=$TURN_ID&after=0"
```

Browser clients should not call the broker directly because the stream requires server-side broker authentication. Product UIs should consume a host-owned stream that proxies broker events.

## Stop the stack

```bash
docker compose \
  -f examples/docker-compose.yml \
  -f examples/docker-compose.local.yml \
  down
```

Broker state persists in the `codex-broker-data` volume unless you remove that volume.

## Native development

Use native `uv` runs when changing broker code or running targeted tests outside Docker:

```bash
export CODEX_BROKER_HOST=127.0.0.1
export CODEX_BROKER_PORT=3400
export CODEX_BROKER_DATA_DIR=.data
export CODEX_BROKER_ALLOWED_WORKSPACE_ROOTS=/path/to/workspaces
export CODEX_BROKER_ALLOWED_BUNDLE_ROOTS=/path/to/bundles
export CODEX_BROKER_ALLOWED_TOOL_COMMANDS=python,node
export CODEX_BROKER_ALLOWED_HOSTED_TOOL_URL_PREFIXES=http://127.0.0.1,http://localhost,http://host.docker.internal
export CODEX_BROKER_INTERNAL_KEY=dev-only-key
export CODEX_BIN=codex
export CODEX_CREDENTIAL_STORE=file

uv run codex-broker
```

For a quick unauthenticated development run, you can set `CODEX_BROKER_ALLOW_UNAUTHENTICATED=true` instead of `CODEX_BROKER_INTERNAL_KEY`. Do not use that in a shared environment.
